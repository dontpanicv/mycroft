The failure case that changes the design

Stock pi-env kills its commands when the connection closes or goes silent for 30 seconds. If iOS suspends the phone-hosted agent, a remote build can be killed too.

For long independent work: submit a job to a server-owned worker with a stable job ID and stored logs/results, then reconnect to that job. Or let a server-hosted agent own the whole run. This is additional architecture, not something pi-env gives you automatically.

pi-env liveness contract

How the iOS app could develop itself

Keep a small native host stable and make the experiment’s JS / web layer replaceable. Start with a personally signed prototype; distribution requirements are a separate constraint.

Ask for a feature→Edit source→Build + validate→Activate version→Resume session
  1. Keep source, runtime bundles and durable data separate.The agent edits a workspace. Build a candidate bundle in a new version directory; it should not overwrite the active runtime piecemeal.
  2. Use a remote build first.Compile TS / web assets on the tool machine and load the result into the development app. Browser compilation with esbuild-wasm is an optional later experiment.
  3. Switch versions at an explicit checkpoint.Let current work settle or be recorded as interrupted, close the old harness, then open the same storage under the new version. Only one harness owns that storage.
  4. Keep a known-working boot path.If loading fails, choose the previous bundle. Back up data before migrations; reverting code alone cannot undo an incompatible schema change.
  5. Treat native changes as builds.Swift, native bridges, entitlements and bundled machine code need a new signed app. The agent can prepare those changes remotely; an Apple-supported installation step remains.

Design proposal informed by storage ownership, JS extension loading, and esbuild’s browser API.

Smallest useful experiment and the tests that decide it

For the closest match, use SwiftUI + the existing PiDurableKit runtime + one remote workspace. Keep the first tool adapter narrow. Add full pi-env coverage only after the loop works.

  1. Prove durable local chat.Use SQLite and a test provider. Kill the app after a committed tool intent, reopen it, and check safe replay versus an interrupted side effect.
  2. Prove the remote boundary.Read, edit and test a small project. Disconnect during execution and display the actual outcome. Label every result with the machine, workspace and revision.
  3. Prove iOS background behavior on hardware.Try a finite run with BGContinuedProcessingTask. Test screen locking, app switching, network changes, cancellation and expiration. Report real progress; handle a request that cannot start.
  4. Prove one self-update.Have the agent add a visible web/UI feature, activate it, and continue the same conversation. Then deliberately break the candidate and verify recovery to the working version.
  5. Choose the operating mode from that result.If background reliability is inadequate, put long jobs—or the whole harness—on the server. Avoid automatic phone/server migration until ownership and synchronization are explicitly designed.

PiDurableKit already exposes native SQLite and custom environments. Its reviewed bundle uses Pi 1.2.0, so pin compatible revisions before testing against the 1.3.0 pi-env code.

Personal installation versus an App Store product

Personally installing a development build makes experimentation easier, but retains the iOS sandbox and signing rules. A fixed native shell with editable interpreted assets is a plausible development design.

For distribution, Apple’s 2.5.2 and 4.7 rules need to be considered together. Some downloadable web apps and plugins are permitted under conditions; unrestricted changes to the host app’s functionality are not automatically covered. A web application accessed in Safari is the cleanest first route for a remotely hosted self-editing experience.

connectSsh detects a supported remote platform and deploys the SHA-256-addressed daemon. File bytes, commands and results travel through its SSH stdin/stdout protocol. Qualified

iOS cannot run a shell

Ordinary iOS apps cannot spawn arbitrary native child processes. But iSH emulates a Linux shell, and apps can expose in-process interpreters and sandbox file tools. Therefore “all hands must be remote” was false. Remote tools are the practical choice for a general native development toolchain.

Corrected

All background work stops within seconds

That is the ordinary suspension model, with exceptions. Since iOS 26, BGContinuedProcessingTask can continue a user-started, finite job with network work. It requires progress and expiration handling, can be cancelled, and is not an always-on daemon entitlement.

Apple task documentation · WWDC details

Qualified

Suspension is just a crash

Suspension may preserve process memory but stops its execution; termination requires reopening persisted storage. Neither grants automatic restart privileges. Provider connections and remote commands can fail while suspended. Durable recovery resumes work when the OS permits execution.
