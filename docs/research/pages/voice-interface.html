How this attaches to Pi Durable

Use a small adapter, not a new audio provider inside Pi. In the inspected revision, Pi's normal message contract handles text/images, not a live audio stream. The native coordinator collects voice context, admits a task through Conversation.submit, and watches message/tool events.

Client delegation needs application context. GPT-Live's delegation event contains an ID, not the task text. Assemble the relevant transcript and app state; associate the delegation with the Pi submission. Deduplicate admission with a stable request ID, rather than sending every partial transcript fragment as a new command.

One owner executes tools. Pi owns tool execution. The voice model receives brief verified results and useful status. For GPT-Live, session.commentary.append supplies information to speak; session.thinking.append supplies quiet context. Do not route the same request into two independent tool loops.

Persist tasks, not audio packets. Store commands, corrections, task IDs, outcomes, and relevant conversation records. Keep live audio processing outside the durable commit loop. Reconnect a fresh audio session after a process restart and restore concise context from the local records.

Preserve the native session during a JS reload. The audio coordinator stays in the stable host while the editable worker changes. In-flight delegations need a durable mapping to task IDs; reattach to pending work instead of replaying desktop actions.

AirPods, lock screen, latency, and cost

Audio route: use .playAndRecord with .voiceChat, voice processing, and a Bluetooth hands-free route. Handle AirPods disconnects and phone-call interruptions. Apple's high-quality Bluetooth recording mode can increase latency and is not its recommendation for real-time communication.

Screen locked: with microphone permission and the audio background mode, an active audio conversation can continue after backgrounding or locking. This is not an unrestricted, permanently listening wake-word service. Start with a user-initiated session and test lock/unlock on the actual AirPods and iPhone.

Fast replies: keep the connection warm, stream audio, tune turn-taking, and let the voice layer acknowledge a request before a long task completes. Measure end-of-speech → first audible reply separately from time to verified task completion. No subsecond guarantee follows from choosing a realtime API.

Session cost: current GPT-Live documentation bills the live session by duration, with backend model/tool usage separate. Design explicit start/stop and idle behavior; do not assume an open, quiet session is free.

The simpler alternative

Streaming speech recognition → Pi → streaming speech synthesis. This closely follows Pi's existing text workflow and allows more component choice. Apple's SpeechAnalyzer/SpeechTranscriber is an on-device recognition option, subject to device/language/model-asset support. It still needs speech playback and turn-taking logic.

The tradeoff is that you manage recognition timing, interruption, and speech output yourself, and the spoken answer often waits on the text agent. It can be made responsive, but full-duplex conversation is more work than adding a microphone button.
